## 1. Summary and method

- **248 named functions** (arrow `const`s and `function` declarations at top level), **198 other top-level statements**, **104 top-level `const`s**.
- **245 `on()` call sites** (W001–W245). Executing the whole worker under stub Roll20 globals produced **431 `on()` registrations carrying 6264 event tokens**, because many sites register generated event lists (per career, per talent, per skill, per scope).
- A *worker* here means either a named function or an `on()` watcher. Functions are listed by name; watchers by an ID that follows source order, so `W077` is always the `sheet:opened` watcher.
- **Called by** entries of the form `W123` are `on()` watchers that call the function inline. Names in backticks are other functions.
- **Method.** Orphans are the named functions with no resolved reference from any root. Roots are every top-level statement and every `const` that runs at load. Identifiers were resolved with scope-aware analysis, not text search, so a name that appears only inside a string or comment does not count as a reference. Each orphan's body was then read by hand (section 2).
- **Not covered.** Data flow through `setAttrs` (which watcher writes an attr another listens to) is not tabulated; see section 7.

### Runtime-conditional registrars (not orphans)

These are only ever *called* from inside other functions or from `afterAllSets`, so a naive reachability scan can mistake them for unused. They are live:

- `registerSkillHandler`, `registerTalentSummaryWatcher` — called per race from `ensureRaceWatchers`.
- `registerCareerSkillLimiter` — called from `registerPrimaryExclusiveSkillWatchers` and `registerActiveSecondaryCareerWatchers`.
- `registerWeaponManualWatchers`, `registerGrenadeManualWatchers`, `registerVehicleManualWatchers` — called from `initializeSheetOnOpen`.
- `registerStatHandler` — called from `bootstrapGlobalWatchersOnce` and again by W192 when a secondary career row is added or removed.

### Dead triggers (events that can never fire)

Event tokens were compared with the `name="attr_*"` and `act_*` elements in the HTML, respecting fieldset scope for repeating sections. Tokens with no matching element can never fire. They cost registrations, not correctness.

- **905 `change:repeating_secondarycareer:<talent>` events** (registered by W014, `registerCareerTalentSummaryWatcher`) have no element: the `repeating_secondarycareer` fieldset (lines 7168–7212) contains only seven attrs, and the career talent checkboxes (e.g. `attr_codeweaver_hardlight_override`, line 7391) are static, outside the fieldset. The *static* events from the same lists are live. Likely an artefact of the generator registering both forms; harmless, but they are about 14% of the 6264 event tokens registered at runtime.
- **41 static career events** with no element: 27 `change:<career>_trail_hardened` and 14 `change:<career>_strain_buffer`. These names exist only as talent DataMap keys; no HTML element carries them.
- `change:bg_<ancestry>_talent` ×8 (one per ancestry) — no `attr_bg_*_talent` element exists.
- `change:used_scene_alteri_social_resonance`, `change:perk_blood_born_survivor_hp_bonus`, `change:_reporder:moneyledger`, `change:reporder:moneyledger` — no element. The `_reporder` pair is Roll20-internal and not expected to match HTML; the other two do not exist in the HTML at all.

**Listen-only attrs (event exists, nothing writes it).** Ten tokens fire only from worker `setAttrs`, with no HTML input: `character_id`, `used_session_perk_blood_born_survivor`, `recompute_nonce`, `weapon1_mdr_mod_penalty_reduce`, `repeating_weaponsmdr:weapon_mod_penalty_reduce_mdr`, `repeating_weaponmanual:weapon_mod_penalty_reduce_mdr`, `cw_smartlink_installed`, `xp_pool_total_talent`, `mag`, `xpledger_recalc_tick`. Of these, `xpledger_recalc_tick` is written by the worker (a timestamp bump), so it is live. `xp_pool_total_talent` is the concern: see section 3.

## 3. Other defects found while mapping

- **Duplicate watcher pair.** W240 and W245 are both `on("remove:repeating_safehouses")`; W245 also calls `updateLocDisplay`. Project rule: fold into one handler. Both recalculate lifestyle totals, so every safehouse removal does the work twice.
- **Duplicate manual-weapon ammo handlers.** W034 and W035 register on the same two ammo events (`weapon_ammo_type_mdr`, `weapon_ammo_active_mdr`) in the manual section. They cannot see each other's writes (project rule: *Check for an existing watcher before registering a new one*). The repeating-weapon section already folds both into one handler (W177).
- **`weapon1` / repeating asymmetry.** W175 (weapon1 ammo) writes label, note, AP and effective damage; W214 separately recomputes the counter and modes. Same split as W034/W035, one scope over.
- **Same step list in three places.** `ensureRaceWatchers → initializeRaceState → updateTalentEnables` appears in `handleRaceChange` (orphan), in `initializeSheetOnOpen`, and in W168. The orphan is the stale copy.
- **Same inline logic in two places.** PC Exhausted/Tired apply/remove: inlined in W111 and again as four orphan helpers.
- **`implicit global`**: `spellDataMap` is referenced without a declaration (resolved at runtime only if defined on the global object elsewhere). Verify before relying on it.
- **`xp_pool_total_talent`**: W011 (`registerXPTrackerWatcher`) listens to it and reads it as the talent XP pool, but no `setAttrs` writes it and no HTML element declares it, so the value is always empty and parses to 0.
- **`recompute_nonce`** is a listen-only trigger on W168; confirm the API script or HTML that is meant to bump it.

## 4. Lifecycle: how the workers start

1. **Load.** The module evaluates top to bottom. Every top-level `on(...)` (the `[top]` watchers) registers immediately. `bootstrapGlobalWatchersOnce` has *not* yet run.
2. **`sheet:opened` (W077)** calls `initializeSheetOnOpen`. It runs `bootstrapGlobalWatchersOnce`, which registers the race-agnostic registrars (perk, flaw, background, talent, XP, career, mirror-skill, trained-skills, stat handler, career prereq text and tab watchers).
3. `initializeSheetOnOpen` then calls `ensureRaceWatchers` / `initializeRaceState` for the selected ancestry, `initCareers`, every `init*Presets`, the cyberware inits, `reconcileAmmoTypes`, the weapon init functions, `registerWeaponManualWatchers`, `registerGrenadeManualWatchers`, `registerVehicleManualWatchers`, and the recalcs (`recalcArmorTotals`, `recalcCtVitalityTotal`, `recalcMoneyLedger`, …).
4. Handlers registered *during* step 2 or 3 are the **runtime-conditional** registrations: they exist only after the sheet has opened. The registration count above includes them.

## 7. Indirect chains (not tabulated)

A write-to-listen chain table was not produced. Mapping runtime registrations back to individual `on()` sites was unreliable for nested registrars (the engine's reported call-site line points at the event-list literal, not the `on(` line), so a table built on it could assert false links. The direct dependencies are the **Calls** columns above. Indirect chains confirmed by reading: W056 (`change:str`) back-calculates `str_base` while `recalcCyberwareBonuses` writes `str`, so the rule that `registerStatHandler` must never write `str` is what prevents a loop; W192 re-runs `registerStatHandler` when a secondary career row is added or removed; preset-select watchers write display attrs that roll buttons later read.
